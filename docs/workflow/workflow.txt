WORKFLOW RUNTIME ATTUALE
========================

Esempio:
"Analizza il testo 'agent agent governance MCP evidence evidence evidence'
e restituisci le parole più frequenti."

1. INTAKE

Layer 1 produce:

{
  "task_spec": {
    "goal": "Calcolare e spiegare le parole più frequenti.",
    "context": "Usare il testo fornito.",
    "constraints": ["Non modificare sistemi esterni."],
    "sensitivity": "low",
    "success_criteria": ["Restituire conteggi corretti e leggibili."],
    "execution_intent": "proposal_only"
  },
  "execution_policy": {
    "confidence_threshold": 0.65,
    "read_only_mode": false
  }
}

Il task strutturato descrive il risultato richiesto. Non contiene una tassonomia
del dominio né una lista separata di operazioni da ricopiare nel runtime.

2. BOOTSTRAP

bootstrap_from_intake crea TaskState:

{
  "current_state": "planning",
  "plan_steps": [],
  "current_plan_step_index": null,
  "observations": [],
  "tool_results_history": [],
  "governance_history": [],
  "tool_call_count": 0,
  "actor_turn_count": 0
}

Goal, contesto, vincoli e criteri di successo restano istruzioni. Non diventano
automaticamente prove.

3. PLANNER

Il planner produce un piano semantico completo:

{
  "plan_steps": [
    {
      "step_id": "step_1",
      "objective": "Calcolare statistiche deterministiche sul testo fornito.",
      "rationale": "I conteggi devono precedere la sintesi.",
      "expected_outcome": "Frequenze delle parole disponibili.",
      "status": "pending"
    },
    {
      "step_id": "step_2",
      "objective": "Presentare i conteggi in una risposta concisa.",
      "rationale": "L'utente richiede un risultato leggibile.",
      "expected_outcome": "Risposta finale con le parole più frequenti.",
      "status": "pending"
    }
  ]
}

Il runtime conserva esattamente questi passi. Non li compatta, non li espande e
non ne inserisce altri.

4. ACTOR - PRIMO TURNO

L'actor riceve l'intero piano, ma può committare soltanto step_1. Propone:

{
  "result_type": "propose_action",
  "plan_step_id": "step_1",
  "summary": "Calcolare le frequenze con il tool read-only.",
  "tool_request": {
    "request_id": "...",
    "plan_step_id": "step_1",
    "tool_name": "mcp.local_test.text_stats",
    "reason": "Servono conteggi deterministici.",
    "text": "agent agent governance MCP evidence evidence evidence",
    "limit": 5
  }
}

5. GOVERNANCE DELLA TOOL CALL

La governance costruisce fatti deterministici. Per una tool call read-only OPA
verifica la static policy; Trajectory resta attivo per la liveness, mentre Evidence
è richiesto solo quando l'evento o lo step trasporta contenuto fattuale. Se la richiesta
è ammessa:

actor -> governance -> tool_gateway

Gli `INTERMEDIATE_OUTPUT` non percorrono questo ramo:

actor -> actor

6. TOOL GATEWAY E MCP

Il gateway valida registry, allowlist, campi e capability. Il server MCP restituisce
il contenuto reale. L'adapter normalizza:

{
  "success": true,
  "summary": "Statistiche calcolate.",
  "content": "{\"top_words\":[[\"evidence\",3],[\"agent\",2]]}",
  "observations": [
    {
      "observation_id": "step_1:tool:1:observation:1",
      "content": "{\"top_words\":[[\"evidence\",3],[\"agent\",2]]}",
      "locator": "mcp://local_test/text_stats"
    }
  ]
}

7. REGISTRAZIONE DELLE OSSERVAZIONI

observe_tool_result verifica e registra l'osservazione senza aggiungere rank,
qualità presunta o categorie semantiche. L'actor riceve al turno successivo il
contenuto esatto, il locator e l'identificatore.

8. ACTOR - COMPLETAMENTO STEP 1

{
  "result_type": "step_completed",
  "plan_step_id": "step_1",
  "output_text": "evidence: 3; agent: 2; governance: 1; MCP: 1.",
  "step_validation": {
    "plan_step_id": "step_1",
    "actor_self_confidence": 0.95,
    "evidence_refs": ["step_1:tool:1:observation:1"],
    "rationale_summary": "I conteggi provengono dall'osservazione MCP."
  }
}

I riferimenti sono opzionali, ma quelli dichiarati devono esistere. La governance
convalida il completamento e il runtime avanza a step_2.

9. ACTOR - COMPLETAMENTO DELL'ULTIMO STEP

{
  "result_type": "step_completed",
  "plan_step_id": "step_2",
  "output_text": "La parola più frequente è evidence (3), seguita da agent (2). Governance e MCP compaiono una volta.",
  "step_validation": {
    "plan_step_id": "step_2",
    "actor_self_confidence": 0.95,
    "evidence_refs": ["step_1:tool:1:observation:1"],
    "rationale_summary": "La sintesi usa i conteggi già osservati."
  }
}

Non esiste un tipo di risultato aggiuntivo per l'ultimo step. Il completamento
dell'ultimo passo, dopo governance, diventa l'output finale canonico.

10. CHIUSURA

Sequenza:

bootstrap_from_intake
planner
actor
governance
tool_gateway
observe_tool_result
actor
governance
actor
governance
finalize_bootstrap
END

Il trace `layer2_trace.v6` registra piano, actor, tool call, observations, governance,
output e la classificazione tipizzata della terminazione (`termination_reason`).
Trace, dashboard e behavioral store sono proiezioni: TaskState resta la fonte di
verità.

VARIANTE CON EFFETTO ESTERNO
============================

Se il task chiede un effetto, per esempio l'invio di una email:

1. execution_intent è execute_after_governance;
2. il planner include ricerca, sintesi e preparazione/invio nella traiettoria;
3. l'actor raccoglie le informazioni tramite tool e registra osservazioni;
4. l'actor produce una bozza tipizzata;
5. il runtime normalizza una ExternalOperationProposal e calcola il digest;
6. OPA richiede il Judge sull'esatto payload;
7. per una email, HITL deve approvare l'esatto digest;
8. l'executor invia al massimo una volta per idempotency key;
9. la receipt registra l'esito esterno separatamente dalle osservazioni.

Formula sintetica:

Il planner decide il cammino.
L'actor esegue il lavoro.
I tool producono osservazioni concrete.
OPA decide il routing governato.
Il Judge valuta la semantica dell'effetto.
L'umano autorizza l'esatto payload quando richiesto.
