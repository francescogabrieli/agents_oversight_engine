Flow Runtime Attuale di Layer 2

01 / 11

Questo deck spiega la porzione di runtime oggi implementata nel repository: come un task passa dall'intake di Layer 1 a un loop di esecuzione governato in Layer 2, come vengono raccolte le evidenze, dove la review umana puo interrompere il run e quali artifact vengono persistiti per audit e valutazione.

Il punto chiave e la disciplina architetturale: planner, actor, governance, esecuzione dei tool, osservazione delle evidenze, HITL e trace export sono contratti separati sopra un unico stato runtime canonico.

Punto di Ingresso

L'intake di Layer 1 definisce il contratto del runtime

03 / 11

Layer 2 non parte dal testo utente grezzo. Parte da un `IntakeResult` canonico prodotto da Layer 1, che include semantica del task, execution policy e metadata di intake.

  • `task_spec` porta goal, context, vincoli, dominio, sensitivity e success criteria.
  • `execution_policy` porta confidence threshold, budget e modalita read-only.
  • `metadata` porta parse status, versioning del parser, warning e missing information.
{
  "structured_task": {
    "task_spec": {
      "goal": "...",
      "domain_type": "research",
      "sensitivity": "medium"
    },
    "execution_policy": {
      "confidence_threshold": 0.65,
      "budget": {"max_steps": 5},
      "read_only_mode": false
    }
  },
  "metadata": {
    "parse_status": "complete"
  }
}
L'intake e esterno a LangGraph. Questo preserva un handoff pulito tra interpretazione controllata del task e orchestrazione runtime live.

Inizializzazione dello Stato

Il bootstrap converte l'intake in `TaskState`

04 / 11

Cosa inizializza il bootstrap

  • Stato runtime corrente e cursore del piano.
  • Contenitori per evidenze, scratchpad e step validation.
  • Storici di governance, oversight e human review.
  • Contatori di tool call e actor turn.
  • Stato tipizzato di `external_communication` quando il dominio di intake lo richiede.

Perche conta

`TaskState` e l'unico contratto runtime. Grafo, dashboard, trace export e layer di persistenza derivano tutti dallo stesso stato invece di mantenere rappresentazioni parallele.

Parse Status Effetto iniziale in Layer 2
complete Il runtime parte in planning.
partial Il runtime parte comunque in planning, ma mantiene flag di intake incompleto.
needs_clarification Il runtime parte in `WAITING_HUMAN_REVIEW` con un percorso di chiarimento tipizzato.

Core Agente

Planner e actor sono separati intenzionalmente

05 / 11
Planner

Traiettoria semantica

  • Produce plan step tipizzati.
  • Imposta il cursore del plan step corrente.
  • Non emette payload concreti per i tool.
  • Rimane la fonte della traiettoria prevista.
Actor

Esecuzione limitata allo step

  • Riceve l'intero piano come contesto.
  • Puo agire solo sullo step corrente.
  • Puo richiedere tool read-only, produrre output locale, chiedere chiarimenti o segnalare replan.
  • Non puo riscrivere il piano da solo.
Questa separazione mantiene leggibili tre traiettorie: traiettoria prevista dal planner, traiettoria eseguita dall'actor e traiettoria osservata dal loop delle evidenze.

Punto di Controllo

La governance combina policy e oversight deterministico

06 / 11

Policy OPA

Applica decisioni hard come `allow`, `allow_read_only`, `ask_clarification`, `require_human_review` o `deny`.

Oversight deterministico

Valuta evidence quality, operational risk e trajectory health usando configurazione esplicita e stato runtime.

Decision combiner

Produce una singola runtime directive come `continue`, `continue_read_only`, `request_more_evidence`, `replan`, `wait_human_review` o `stop`.

Vincolo implementato

L'oversight puo preservare o irrigidire la policy. Non puo rendere una decisione OPA piu permissiva.

Limite esplicito attuale

Il futuro semantic judge non fa parte della baseline corrente. Oggi la governance e OPA piu oversight deterministico, non OPA piu judge.

Loop di Esecuzione

Tool gateway e observed evidence chiudono il loop

07 / 11
1

L'actor emette un `ToolRequest` tipizzato solo dopo il planning e prima di qualunque capability call esterna.

2

La governance decide se la richiesta puo continuare, se deve restare read-only o se deve fermarsi, ripianificare o fare escalation.

3

Il Tool Gateway valida la configurazione del registry, risolve il backend, esegue la richiesta read-only e normalizza il risultato in `ToolExecutionResult`.

4

`observe_tool_result` converte il risultato del tool in `ObservedEvidence` esplicita, preservando provenienza e support level per il reasoning successivo.

5

L'actor riceve l'evidenza e continua lo step, lo completa con validation oppure segnala che la traiettoria deve cambiare.

MCP e utilizzabile solo come backend governato dietro il gateway. L'actor non diventa mai un client MCP aperto.

Percorso di Escalation

HITL e selettivo, tipizzato e resumable

08 / 11

Quando il runtime si ferma

  • La policy richiede esplicitamente human review.
  • E richiesto un chiarimento prima di una continuazione sicura.
  • L'operational risk e troppo alto per una continuazione autonoma.
  • `external_communication` raggiunge una fase gated da review.

Cosa esiste oggi

  • Richieste e decisioni di human review tipizzate.
  • Percorso LangGraph `interrupt / resume` tramite `human_review`.
  • Dashboard snapshot sullo stesso contratto di review.
  • Auto-launch della dashboard locale al primo pause di review.
Decisione Canonica Significato
approve_continue / approve_continue_read_only / modify_and_continue Riprende il runtime nella modalita approvata.
request_more_evidence / replan Riprende, ma con un branch successivo piu conservativo.
ask_clarification Mantiene il run in pausa finche l'ambiguita non viene risolta.
abort Termina il run in `ABORTED`.

Stato e Artifact

Persistenza, stato dashboard e trace restano allineati

09 / 11

Persistito a runtime

  • Checkpoint LangGraph locali e durevoli su disco.
  • Runtime artifact per thread sotto artifacts/runtime/<thread_id>/.
  • Payload HITL pendenti e dashboard snapshot.
  • Runtime summary e trace JSON esportate.

Disciplina architetturale

La dashboard e un piano di controllo read-only sopra `TaskState`. La trace e un artifact di audit derivato. Nessuno dei due deve diventare una seconda fonte di verita.

Storici di stato

`governance_history`, `oversight_history`, `human_review_history`, `step_history`.

Record di esecuzione

`executed_steps`, `step_validations`, `scratchpad`, `tool_results_history`, `observed_evidence`.

Contatori operativi

`actor_turn_count`, `tool_call_count`, current plan-step cursor, and runtime flags.

Superficie di Trace

Il trace export rende il runtime ispezionabile dopo il run

10 / 11

`trace.py` costruisce una trace di runtime tipizzata e JSON-safe a partire da `TaskState`. Viene usata per debugging, evidenza di tesi, payload dashboard, artifact persistiti e valutazione offline.

  • Include intake summary, plan steps, actor snapshot, tool calls, evidence, governance decisions, oversight assessments, dati HITL e summary di `external_communication`.
  • Preserva una separazione esplicita tra stato runtime live e viste di audit post-run.
  • Supporta il compact trace export senza ridefinire il contratto runtime.
{
  "runtime": {"thread_id": "...", "current_state": "completed"},
  "plan_steps": [...],
  "tool_calls": [...],
  "observed_evidence": [...],
  "governance_decisions": [...],
  "oversight_assessments": [...],
  "human_review": {...},
  "external_communication": {
    "phase": "draft_proposal",
    "last_transition_summary": "..."
  }
}

Condizioni al Contorno

`external_communication` esiste come stato, non come esecuzione esterna live

11 / 11

Significato attuale

  • Il runtime traccia fasi tipizzate come `evidence_collection`, `draft_proposal`, `human_review_required`, `approved_for_execution` e `blocked`.
  • Queste fasi sono visibili in `TaskState`, nel dashboard snapshot, negli artifact persistiti e nella trace esportata.
  • OPA puo richiedere review quando esiste una draft proposal locale.

Limite attuale

  • Nessuna external send o write execution reale e ancora implementata.
  • `approved_for_execution` significa tracking di stato approvato, non consegna automatica.
  • Il boundary di review e implementato prima di qualunque futura superficie di azione outward.
